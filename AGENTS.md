# Working on Sider

## Scope and architecture

- Read `PLANO.md`, `README.md`, `ROADMAP.md`, and `docs/compatibility.md` before implementing.
- Work on technically unblocked tasks in stages that compile and can be tested.
  R01–R10 are internal milestones; their checkpoints do not require publication. Use up to
  three workstreams in separate worktrees, with one integrator for shared contracts.
- Create modules when they have real implementations; avoid stubs and empty directories.
- Preserve the boundaries between RESP, commands, storage, and networking.
- Use binary data for keys and values. Do not restrict the protocol to UTF-8.
- Storage will be owned by the worker, with bounded channels.
- Do not promise compatibility or performance without reproducible evidence.

## Backlog and releases

- `releases/plan.json` is the source of IDs, dependencies, and criteria; `ROADMAP.md` is
  generated by `cargo xtask roadmap --write`.
- Read `docs/releases.md` before changing automation or preparing a release.
- CI and automatic publication are deferred until after 1.0. The workflows and
  Python helpers were removed; do not restore them or reactivate CI unless requested.
- The database, tests, and project tools use Rust. `xtask/` has its own manifest and lockfile;
  do not add its dependencies to the server.
- When changing the plan or `xtask/`, run `cargo xtask check --tools`.
  `cargo xtask sync` only simulates; `--apply` allows changes to the GitHub backlog.
  Do not create another publication framework while publication remains manual.
- Preserve task IDs, managed markers, and human comments when synchronizing.
- Do not treat bootstrap tests as evidence for future functionality.
- Missing, skipped, or canceled gates block publication; never fabricate success.
- Only R11 publishes a candidate and final release. The package already identifies itself as `1.0.0`
  in the RC; the final release promotes the same SHA and all the same files, without rebuilding
  or rerunning gates. Any bundle change requires another candidate.
- Manually publish the build from the exact preparation merge SHA. Merging publishes nothing.
  Keep the repository and artifacts private and retain `publish = false`.
  Internal checkpoints close after technical validation; R11 closes after verifying the final release.
- Preserve evidence by task/SHA at internal milestones and the R10 baseline for migration.
  Do not attribute old results to a different SHA or alter historical releases.

## Rust and tests

- Respect `rust-toolchain.toml` and keep `Cargo.lock` under version control.
- When changing production dependencies or the toolchain, review the distribution notices
  in `releases/licenses/` and their inventory before the next publication.
- Keep `#![forbid(unsafe_code)]` in project code.
- Add dependencies when there is a real consumer.
- Test relevant behavior and limits alongside the implementation.
- Inject configuration reads in tests. Do not modify the global environment.
- Use ephemeral ports and explicit synchronization in network tests.
- During implementation, run focused tests (`cargo test --locked <filter>`).
  Before integrating database changes, run `cargo xtask check`: fmt, Clippy,
  binary build, and native tests. Clippy already checks the targets; do not duplicate
  it with `cargo check` in this sequence. Do not wait for CI to integrate PRs.
- Validate documentation-only changes without rerunning the entire database suite. Run tool tests
  only when the tools, their contracts, or their manifest change.
  Preserve Cargo caches and run external gates only when relevant to the task or required for a release.
- Run an integrated test suite when completing the durable core with shards/transactions;
  the next full suite is for the 1.0 candidate build, including a 3600 s soak.
  Benchmarks must not share the machine with builds or load tests.
- Also run `cargo doc --locked --no-deps` and `cargo build --locked --release`
  when changing interfaces, build configuration, or API documentation.

## Text and Git

- Write documentation and user-facing messages in English, with correct spelling and punctuation.
- Preserve identifiers, paths, commands, and URLs exactly as defined.
- Check UTF-8 and fix mojibake before publishing text.
- For GitHub Markdown text through the CLI, prefer a UTF-8 file with `--body-file`.
- Use the `organize-atomic-commits` and `conventional-commit` skills when preparing commits.
- Separate independent responsibilities; every integrated commit must pass
  the validation for its stage.
- Do not commit or push unless requested or part of an explicitly authorized workflow.
- Preserve preexisting changes and stage explicit paths.
- Prefer a merge commit when no merge strategy is specified.
- Record local commands, their results, and validation limitations in the PR.
- When leaving uncommitted changes, report an atomic commit plan.
