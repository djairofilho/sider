# Sider 1.0.0

An in-memory database server written in Rust, with an explicit Redis subset over
RESP2/TCP. The package identifies itself as `1.0.0` starting with the candidate.
These notes describe capabilities and limitations; quantitative results and build
identity belong to the release manifest and evidence ZIP. Candidate approval is
recorded outside this immutable set.
The presence of this text alone does not declare any gate passed.

## Capabilities

- Strings and multikey operations, `SET` with NX/XX/EX/PX/GET/KEEPTTL, increments,
  passive/active TTL, and a logical quota that rejects growth without eviction.
- Hashes, lists, sets, and sorted sets, with binary keys, fields, members, and values,
  type errors, and memory and response limits.
- Fixed shards with owning workers, bounded queues, and hash tags. Multikey commands
  and transactions require all keys to belong to the same shard.
- `MULTI`, `EXEC`, `DISCARD`, `WATCH`, and `UNWATCH`, with one AOF batch per EXEC.
  Individual execution errors do not roll back valid commands in the batch.
- Pub/Sub over binary channels, per-connection subscriptions, and bounded queues.
  Messages are ephemeral and local; they are not part of the AOF or replication.
- Optional AOF with checksums, resolved mutations, recovery before binding,
  global compaction, and `always` and `everysec` policies. The reader accepts
  v1/v2/v3 headers; the persistence format has its own version.
- Asynchronous Sider → Sider replication, consistent snapshots, bounded history,
  resumption when available, read-only replicas, and durable manual promotion.
- Backup during traffic, integrity verification, and restore into a new directory,
  preserving all five types, complete batch effects, and absolute TTL.
- `INFO`, configuration diagnostics with `sider --diagnose`, file-based readiness,
  logs, and configurable limits for connections, queues, and network operations.

Complete command forms and intentional differences are documented in
`docs/compatibility-matrix.md`, in the checkout at the SHA identified by the manifest.
The differential reference is Redis and `redis-cli` 8.10.1, Linux amd64, pinned by
digest in `releases/plan.json`. Full compatibility with Redis or clients requiring
initialization commands outside the matrix is not promised.

## Running

Check `SHA256SUMS`, read `runtime-requirements.md`, and extract your platform's
package. Rust and Cargo are not required to run the four programs:
`sider`, `sider-aof-migrate`, `sider-backup`, and `sider-replica`.

- Windows 11 x64, MSVC: run `.\sider.exe --version` and `.\sider.exe` in PowerShell.
  Requires Visual C++ v14 Redistributable x64 compatible with the toolchain and
  up-to-date Windows components; Microsoft DLLs are not included in the ZIP.
- Ubuntu 24.04 x86_64 GNU: run `./sider --version` and `./sider`. The binary is
  dynamically linked and requires the loader and system libraries listed in
  the requirements.
- The private Docker image contains the same four binaries as the Linux package,
  without rebuilding, and runs as an unprivileged user. See `docs/docker.md`
  for loading, persistence, and configuration.

The default RESP address is `127.0.0.1:6379`; Ctrl+C initiates shutdown.
Redis and `redis-cli` are installed separately. Client example:

```sh
redis-cli -2 -h 127.0.0.1 -p 6379 SET example value EX 60
redis-cli -2 -h 127.0.0.1 -p 6379 GET example
redis-cli -2 -h 127.0.0.1 -p 6379 TTL example
```

Without `SIDER_AOF_DIR`, data exists only in memory. With AOF, use a directory
exclusive to the instance and check the sync policy. Replication, TCP backup,
and replica administration require AOF and a separate internal listener.

## Contracts and limitations

The supported environment is controlled. There is no authentication, ACL, or TLS.
Keep listeners on loopback or a private network with controlled access. Redis Cluster,
Sentinel, automatic failover, online resharding, RESP3, Lua, blocking operations,
and cross-shard transactions are out of scope.

The default total logical quota is 64 MiB, divided among shards; it does not bound
RSS, buffers, or snapshots. The default uses one shard. Queues, connections, frame
sizes, and responses have their own limits. An oversized response or timeout may
close the connection after the command has been accepted. The client may then be
unable to determine the outcome; there is no rollback or automatic retry.

With `always`, the response waits for local sync. `everysec` acknowledges after
writing and synchronizes periodically; I/O delays can extend the loss window.
No primary response waits for a replica. Primary failure or manual promotion may
lose data that the replica has not yet applied. Process termination tests are not
equivalent to device power failure tests.

Replication requires the same Sider version and shard configuration. It does not
use the Redis replication protocol. Machine clocks must be synchronized to interpret
absolute expiration times. Replication between different versions is not promised.

## Baseline and upgrade

The R10 internal baseline originates from SHA
`0021d875dde9da6cbbe9b5b84cd640681128e6ea`, with package `0.1.0`. Its manifests,
actually observed hashes, and migration results for the candidate build are included
in its evidence. The candidate does not reuse approvals from another SHA.

The procedure uses fresh copies of the frozen data. To restore an R10 backup, first
run the source's frozen `sider-backup` CLI, then open the restored directory with the
new server. The backup CLI requires the same version as the backup manifest.
Recreate the replica with the new version; preserve the source for recovery.
Downtime consumes TTL. The complete runbook is in `docs/internal-baseline.md`;
layout changes use `docs/aof-migration.md`.

Read timings, counts, throughput, latencies, and memory consumption in the evidence
ZIP, alongside each run's environment and configuration. Candidate approval requires
the full gate matrix, including migration on both platforms, a real Docker image,
a soak of at least 3600 seconds, and benchmarks.

Publications `v1.0.0-rc.N` and `v1.0.0` use the same SHA and the same nine files.
The final release promotes the approved set without rebuilding, repackaging, or
rerunning gates. Any change to the SHA or files requires another candidate;
approval and promotion records remain outside the immutable set.

Project code uses the MIT license; dependencies retain their notices in
`licenses/`. The repository, image, and other files remain private.
`publish = false` remains enabled, with no crates.io publication. CI and automatic
publication remain deferred until after 1.0.
