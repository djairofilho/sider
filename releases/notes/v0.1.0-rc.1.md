# Sider v0.1.0-rc.1

First functional Sider candidate, an in-memory database server written in Rust.
Experimental use in a controlled environment. This version provides neither
persistence nor authentication and must not be exposed to the internet.

## Delivered

- Incremental RESP2/TCP: `PING [message]`, `ECHO message`, `GET key`, basic
  `SET key value`, and `DEL key [key ...]`.
- Binary keys and values, including empty, NUL, and non-UTF-8 bytes. Command names
  are ASCII case-insensitive; keys distinguish every byte.
- Multiple connections, per-connection ordered pipelines, one owning worker, a
  bounded queue, protocol limits, and configurable timeouts.
- `--help`/`--version` CLI, `SIDER_*` configuration, optional file-based readiness,
  and supervised shutdown.
- Native Linux/Windows tests, comparison with Redis and redis-cli 8.10.1,
  AddressSanitizer fuzzing, and smoke testing of extracted executables.

## Install and try it

Download the package for your system and `SHA256SUMS`, verify its hash, and extract
the archive. Rust and Cargo are not required to run the server.

- GNU Linux x86_64: `.tar.gz` package, built and tested on Ubuntu 24.04. Inside
  the extracted directory, run `./sider --version` and `./sider`.
- Windows x86_64 MSVC: `.zip` package. In PowerShell inside the extracted
  directory, run `.\sider.exe --version` and `.\sider.exe`.

The default address is `127.0.0.1:6379`. Use Ctrl+C to stop. In another terminal,
with redis-cli installed separately:

```sh
redis-cli -2 -h 127.0.0.1 -p 6379 PING
redis-cli -2 -h 127.0.0.1 -p 6379 SET example value
redis-cli -2 -h 127.0.0.1 -p 6379 GET example
redis-cli -2 -h 127.0.0.1 -p 6379 DEL example
```

## Contracts and limitations

There are no TTL, dataset quota, eviction, persistence, replication, or collection
types. All data is lost when the process exits. Writes can exhaust memory even when
network limits are respected.

The protocol accepts only non-empty arrays of non-null bulk strings. There are no
inline commands, RESP3, `SELECT`, `AUTH`, `HELLO`, `CLIENT`, or `COMMAND`. Clients
that require those initialization commands may not work. Additional `SET` options
return `ERR unsupported SET options` without mutation. `ERR unknown command` uses
simplified text. Invalid framing, formats outside the subset, and exceeded limits
close the connection.

Defaults allow 32 connections and 32 commands waiting for the worker, 1 MiB bulk
strings, 4 MiB input frame/buffer and response, a 1,024-byte line, 1,024 nodes,
and depth 16. Timeouts are 10 seconds to form a frame and 5 seconds for response
waiting, writing, and draining. Idle connections do not expire.

After a command enters the worker queue, timeout or disconnection can leave its
result unknown to the client. There is no automatic retry or rollback. Draining is
cooperative and provides neither durability nor a guarantee after forced exit.
There is no TLS or ACL; binding outside loopback only emits a warning.

## Validation and artifacts

Publication uses the exact SHA of the release-PR merge, with local validation and
no CI. `release-manifest.json` records SHA, tools, targets, commands, and results.
Attached receipts and logs distinguish native tests, compatibility, at least 900
seconds of fuzzing, and smoke tests of extracted packages. The implementation's
initial fuzz run does not replace this candidate's gate.

The reference is Redis and redis-cli 8.10.1, Linux amd64, pinned by digest in the
[manifest for this version](https://github.com/djairofilho/sider/blob/v0.1.0-rc.1/releases/plan.json).
No full Redis compatibility or performance-superiority claim is made.

See the [compatibility matrix](https://github.com/djairofilho/sider/blob/v0.1.0-rc.1/docs/compatibility.md),
[network guide](https://github.com/djairofilho/sider/blob/v0.1.0-rc.1/docs/network.md),
and [testing guide](https://github.com/djairofilho/sider/blob/v0.1.0-rc.1/docs/testing.md).

Project code uses the MIT license. Repository and release artifacts are public; there
is no crates.io publication. This candidate is not marked latest. The 0.1.0 final
requires this RC's approval and a new build/validation. Functional changes require
another candidate.
